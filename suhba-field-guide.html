1 · Topology

One monorepo, two deploy targets, one database — and two API paths that behave differently.

The repository is named suhba-frontend but holds both applications. Render builds the backend from backend/Suhba; Cloudflare Pages builds the front end from frontend/suhba. Both deploy on push to main via each provider's own git integration — there is no CI anywhere in the repo.

Why the proxy exists

This is the most important structural decision in the codebase, and it is well documented in the source. Admin authentication uses session plus CSRF cookies. The front end (Cloudflare) and backend (Render) are different sites, so those cookies are cross-site — and Safari and iOS block cross-site cookies outright, regardless of SameSite=None; Secure. Routing /api/* through the front end's own origin makes them first-party, so admin login works in the iOS PWA.

Public reads skip the proxy: the four public services build absolute URLs from VITE_API_BASE_URL and hit Render directly. That is safe because /api/v1/** is configured allowCredentials: false, so no cookie can ride along. Note the asymmetry, though — the Function is a catch-all that would proxy any /api/* path. Only client convention keeps public traffic off it.

2 · Findings

Ranked by exploitability, then by user-visible impact. Every item was traced to source.

Critical & high

Anyone can overwrite any listing

Critical Unauthenticated

All three DTOs expose id, and no mapper ignores it on the inbound path. The mappers ignore status, upvotes, featured and the timestamps — but id passes straight through. submit() then calls repository.save(entity), and Spring Data's save() with a non-null id performs a merge — an UPDATE, not an INSERT. 

# Unauthenticated. Overwrites prayer spot 5 and hides it from every listing.
curl -X POST https://suhba-backend.onrender.com/api/v1/prayer-spots \
  -H 'Content-Type: application/json' \
  -d '{"id":5,"name":"…","address":"…","district":"…",
       "latitude":48.2,"longitude":16.3,"type":"MOSQUE"}'

Ids are sequential, so all 412 halal spots, 76 prayer spots and every event are individually addressable. The whole community-curated directory is editable by anyone who finds the endpoint. created_at survives only because that column is updatable = false.

Fix: one line per mapper — @Mapping(target = "id", ignore = true).

PrayerSpotDto.java:13 · PrayerSpotMapper.java:15-19 · PrayerSpotServiceImpl.java:55-61 · same shape in HalalSpotMapper, EventMapper

Public schema was exposed through Supabase PostgREST

Fixed in V15

Supabase auto-exposes the public schema as a REST API and pre-grants anon/authenticated table privileges, gated only by row-level security. Because Flyway creates tables with plain CREATE TABLE — unlike the dashboard's table editor, which enables RLS by default — RLS was off on all six app tables and on flyway_schema_history. That made the BCrypt hashes in admin_users readable with the project's public anon key.

V15__lock_down_public_schema.sql enables RLS on all seven tables and revokes the grants outright, including schema-level USAGE and the default privileges that would re-expose future tables. Statements are idempotent and guarded on role existence, so the migration is a no-op on the plain Postgres used for local dev.

Mitigating context: the anon key was never published. No client ever used Supabase directly, and full git-history scans found no key, password, or connection string in any commit. The door was unlocked; the address was never handed out.

db/migration/V15__lock_down_public_schema.sql · verified: anon denied, owner unaffected, idempotent, safe on local dev

Unmoderated content is publicly readable by id

High

Every listing endpoint filters status = APPROVED, but getById has no status filter on any of the three resources. PENDING and REJECTED submissions — including anything a moderator explicitly rejected — are fetchable by sequential id from the public API.

PrayerSpotServiceImpl.java:65-69 · HalalSpotServiceImpl.java:76-80 · EventServiceImpl.java:63-67

Upvotes are unauthenticated, undeduplicated, and racy

High

upvote(id) is a read-modify-write with no @Transactional, no @Version, no per-user dedupe, and no rate limit. Anyone can drive any record's upvotes arbitrarily high — and upvotes DESC is the second sort key in the halal bounding-box query, so this directly manipulates directory ranking. It also works on PENDING and REJECTED records.

PrayerSpotServiceImpl.java:86-90 · HalalSpotRepository.java:21

Swagger UI is public in production

Medium

/swagger-ui.html and /v3/api-docs/** are permitAll() with no profile-conditional disable, so the full admin API surface is documented at a public URL on the live backend.

CSRF is disabled across /api/v1/**, which includes admin-gated paths

Medium

CSRF is ignored for /api/v1/** on the reasoning that the public API is session-free. But /api/v1/*/approve, /reject and /pending live under that same prefix and are session-authenticated. Cross-site exploitation is blocked only by allowCredentials: false on that CORS registration. These endpoints duplicate /api/admin/* and could simply be deleted.

X-Forwarded-For is trusted unconditionally

Medium

The login rate limiter keys on the first X-Forwarded-For entry with no check that the request actually came through Render's proxy, so the 5-failure lockout can be sidestepped by rotating the header. The limiter is also per-instance and in-memory, and free-tier cold starts reset it constantly.

No spam protection on the three public submit endpoints

Low

No honeypot, CAPTCHA, server-side rate limit, or client throttle on POST /api/v1/{prayer-spots,halal-spots,events}. The only guard is a disabled button while a request is in flight. Moderation is the sole line of defence.

3 · Front end

React 18 + Vite 5 PWA · ~10,080 lines of TS/TSX · 48 test files, 342 tests passing.

  • 0 router libraries
  • 0 state libraries
  • 0 uses of localStorage
  • 1 locale (de)

Stack

react/react-dom 18.3, leaflet 1.9 + react-leaflet 4.2, i18next 26 + react-i18next 17, @phosphor-icons/react 2.1, @tanstack/react-virtual 3.13. Tailwind 3.4 for styling; Vitest 2.1 with happy-dom for tests; vite-plugin-pwa 0.21 for the service worker.

Five dependencies are installed and never imported

adhan (4.4.3) and all four @fortawesome/* packages have zero import sites. Prayer times are not computed locally — no calculation method, no madhab, no coordinates. They come from the backend's seeded 2026 IZW calendar. Icons are all Phosphor. Removing these five is safe.

Routing — there isn't any

No react-router. Three mechanisms substitute:

  1. Root selection — main.tsx:5 does window.location.pathname.startsWith('/admin') and picks one of two createRoot calls. The admin bundle therefore never loads i18n, which is why all admin copy is hardcoded.
  2. Public "routes" — five useState values in App.tsx:16-20: one NavTab plus three selection ids plus an active-form flag. Detail views are <Modal> overlays, not routes.
  3. Admin "routes" — a three-state machine (loading | unauthenticated | authenticated) in AdminApp.tsx:7-49, with the dashboard's own tab as local state.

Consequences: nothing is deep-linkable or shareable; switching tabs unmounts the page and destroys its filters, view mode, dhikr index and counter progress; and AdminApp treats any me() rejection as unauthenticated, so a 500 or network outage is indistinguishable from a 401.

Service layer

Six services in src/services/, all network I/O. The base URL is defined seven separate times in two different shapes — four services append /api/v1, while prayerTimesService and the three submit hooks inline the segment at the call site. http://localhost:8080 is the fallback everywhere, so a missing env var in a production build silently targets localhost.

CSRF handling, exactly

There is no bootstrap fetch. The token arrives as a non-HttpOnly XSRF-TOKEN cookie on any response — in practice the first GET /api/admin/me seeds it. It is stored only in the cookie jar, regex-scraped from document.cookie at request time, and attached as X-XSRF-TOKEN on non-GET/HEAD requests. A missing cookie yields a silent empty string, the server 403s, and the user sees a generic "Action failed" with no retry or re-bootstrap.

Errors are wrapped with Object.assign(new Error(…), { status }), which is what lets the login page and dashboard branch on HTTP status. There is no runtime validation of any admin response and no 401 interceptor.

src/api/index.ts is 128 lines of dead code

A fully typed client (prayerSpotsApi, halalSpotsApi, 16 methods) with zero call sites. It is also the only place the X-User-Id header is sent — so because the submit hooks fetch inline instead, that header never actually goes out and every submission is attributed "anonymous" server-side.

Feature modules

Vertical slices under src/features/: home, prayers, spots, halal, events, azkar, submit, admin. Two domain models coexist — a German-labelled UI model in src/types/index.ts (SpotType = 'Moschee' | 'Gebetsort' | 'Sonstige', string ids, lat/lng) and the backend wire types (uppercase enums, numeric ids, latitude/longitude). Services translate between them, lossily in places.

Submit flows

Three single-page forms, presence-only validation on 4–5 fields. Spot and business forms geocode via Nominatim (duplicated verbatim); the event form does not geocode at all. No length, format, or date-ordering checks. The response body is discarded, so a submitter never sees their pending entry.

Admin dashboard

779 lines containing 10 components and 14 pieces of local state, with editData: Record<string, unknown> cast at each call site. It loads all records and derives pending-ness client-side, which makes the three pending* service functions dead. Its error handling is the most careful in the codebase; its PUT sends the whole record including status.

Notable feature-level quirks: the events filter is a single flat union ('Alle' | 'Heute' | 'Diese Woche' | EventCategory), so time and category filters are mutually exclusive — which is why the filter badge is a hardcoded 1. Search emptiness is checked on query.trim() but matching uses the untrimmed value, so "  gebet  " never matches. 'Sonstige' events are submittable but omitted from the filter list. There is no recurrence support anywhere — a weekly Juma must be entered as N separate events.

State & i18n

No global store, no Context, no reducer — zero createContext hits. Everything is local useState plus one module-level cache: a promise keyed by Vienna date in usePrayerTimes.ts:16-17, which deduplicates the three prayer-time consumers into a single request. Spots, halal and events refetch on every mount.

Nothing is persisted. No localStorage, sessionStorage, or IndexedDB anywhere. The last geolocation, the dhikr index, the azkar tab, and tasbīḥ counter progress are all lost on reload — and on tab switch, since pages unmount.

i18n is German-only: one de.json (304 lines), no en.json, no switcher, no detector. There is no pluralisation, so "1 Orte" renders in the singular case; azkar.repetitions is fed the string "33×" through i18next's reserved count key. A substantial amount of German bypasses i18n entirely — all five prayer names, the geolocation banner, aria-label="Sortierung", every raw enum rendered as a chip, and the whole src/data/ content layer.

RTL is applied per Arabic text node across eight sites rather than at the document level; <html lang="de"> has no dir. Amiri is loaded from Google Fonts and applied through two competing idioms (a font-amiri class and an inline fontFamily).

PWA, maps, styling

registerType: 'autoUpdate' with the generateSW strategy. Precaches 25 entries. Four runtime-cache rules cover Google Fonts, gstatic, and OSM tiles — plus one for api.masjidiapp.com, an API the app never calls. There is no rule for the Suhba backend, and no localStorage, so the app is shell-only offline: prayer times error out, all lists are empty.

No virtual:pwa-register import and no beforeinstallprompt listener, so there is no custom install prompt, no update toast, and no offline indicator — installation relies entirely on the browser's native affordance.

Three Leaflet components, each lazily loaded with <Suspense> but no per-boundary error boundary, so a chunk-load failure blanks the tab. SpotsMap allocates a fresh L.DivIcon per marker per render, has no clustering (hundreds of DOM markers over a 15 km radius), and never recenters on the user or on filtered results because react-leaflet v4 treats center/zoom as initial-only.

Palette drift

Tailwind and index.css describe the current dark-green scale (#051F20 … #DAF1DE), but an older olive/cream palette survives hardcoded in three places: map pin colours (#485530, #5A6840, #B89A70), the spinner's CSS-var fallbacks, and the PWA theme_color/background_color. So map pins and the install splash render in the previous palette while the app renders dark green.

4 · Back end

Spring Boot 3.3.4 · Java 17 · MapStruct + Lombok · 13 test classes, no @SpringBootTest.

Layering, as actually enforced

  • Every service is an interface in services/ with one @Service impl in services/impl/; controllers depend only on the interface.
  • Entities never leave the service layer — controllers return DTOs exclusively. One leak: HalalSpotController:35 accepts an entity enum as a request param, and all DTOs import their enums from the entity classes, so nested entity enums are part of the public JSON contract.
  • jakarta.* only; no javax.* anywhere.
  • distanceKm is computed per request, never persisted.
  • No @Transactional anywhere. Every repository call runs in its own transaction. This is why HalalSpotEntity.cuisines must be EAGER — mapping happens outside any transaction — and why default_batch_fetch_size was needed.
  • boundingBox() and haversine() are private and duplicated verbatim in three impls.

Build-order detail worth preserving: annotationProcessorPaths lists Lombok before mapstruct-processor. MapStruct reflects over getters and setters, so Lombok's accessors must exist when it runs. Reversed, MapStruct emits mappers that silently copy nothing — and there is no lombok-mapstruct-binding on the path, so the explicit ordering is the only thing making this work.

Five entities, zero JPA associations. The only relational mapping is an @ElementCollection for HalalSpotEntity.cuisines. All five are independent aggregates; submitted_by is free text, not a foreign key.

The /api/v1 admin endpoints are unreachable from the admin SPA

/api/v1/** is configured allowCredentials: false, so a browser cannot send the session cookie there. The ADMIN-gated /pending, /approve and /reject under that prefix are therefore dead to the front end, which uses the /api/admin/* equivalents. They are duplicate surface area — and, per §2, they are also CSRF-exempt.

Error contract

Uniformly a flat {"error": "…"} map. BLException → 400, DALException → 500 (message suppressed), validation failures → 400 with joined field errors. 404 is never produced — a missing entity is a 400, which the tests codify. DALException is never thrown anywhere, so its handler branch is unreachable. There is no @ExceptionHandler(Exception.class), so unexpected throwables fall through to Boot's default shape.

Geo & moderation

Nearby queries use a flat bounding-box prefilter (latDelta = radiusKm / 111.0, lngDelta = radiusKm / (111.0 · cos lat)) so Postgres can use the location index, then exact haversine in Java on the reduced set. No clamping for poles or antimeridian — correct for Vienna, wrong globally. Distances are rounded to 2 dp before the radius filter, so a spot at 5.004 km is included at radiusKm=5.0.

Sorting differs per resource, which the API shape does not hint at: prayer spots sort by pure distance; halal spots sort by distance then featured — but only within an exact 2-decimal tie, so featured prominence really comes from the repository's ORDER BY featured DESC, upvotes DESC; and /events/nearby sorts chronologically, not by distance.

Because the halal import used district centroids rather than street addresses, hundreds of rows share exact coordinates — which is what makes the distance tie-break meaningful at all, and what makes distance ordering within a district essentially arbitrary.

Moderation: submit() forces status=PENDING, upvotes=0, featured=false, and submittedBy from the header, ignoring whatever the caller sent. approve/reject are bare state sets with no guard that the current status is PENDING, so they are freely reversible. Admin update() is a full replace with no null-guard, and silently drops fields — the prayer-spot updater never writes jumaTimeSummer, jumaTimeWinter, language, or googleMapsUrl, all of which the V7 import populated.

Test coverage gaps

342 front-end tests and 13 back-end test classes pass, but the security layer is untested: nothing covers SecurityConfig, AdminInitializer, LoginRateLimitService's actual arithmetic, AdminUserDetailsService, any mapper, or the admin CRUD endpoints. Critically, @WebMvcTest with addFilters = false means @EnableMethodSecurity is inactive in the web slice — so no test verifies that any admin-gated endpoint rejects an anonymous caller. And because the test profile disables Flyway and builds the schema from entity metadata on H2, the migrations are never validated by any test.

Secrets audit — clean

Full git-history scans for passwords, keys, connection strings, and Supabase hostnames returned only change_me placeholders from .env.example. The root .env has never been committed; application-local.yml is untracked; the two tracked .env files contain only public URLs. The pool number, and why Flyway depends on it

# application.yml:15-24
hikari:
  # The production DB sits behind a session-mode connection pooler capped at
  # 15 client connections. Keep this app's pool small so a rolling deploy
  # (old instance + new instance booting) plus Flyway stays under that limit.
  maximum-pool-size: 3
  minimum-idle: 1
  max-lifetime: 120000

Supabase's session-mode pooler pins one upstream backend per client connection for the whole session — it does not multiplex — so 15 is a hard wall. And Spring Boot's Flyway auto-configuration reuses the application DataSource when no spring.flyway.url is set, which it isn't. So Flyway's migration connection comes out of that same pool.

At pool 3, a rolling deploy needs 3 + 3 = 6 of 15 and Flyway gets a connection immediately. At Hikari's default of 10 it needs 20 of 15: the pooler refuses, Flyway blocks for the 30-second timeout and throws, and application startup aborts. The new instance never passes the health check, Render keeps the old one, and the deploy silently fails to roll out. That is the failure this number prevents.

default_batch_fetch_size: 100 solves the companion problem. Because cuisines is EAGER and there are no transactions, one query for 412 halal spots triggered 412 follow-ups across the internet — about 50 seconds. Batching collapses that to five IN queries.

Both of these are load-bearing and non-obvious. If the backend ever moves to a paid plan with multiple instances, the pool number must be re-derived, not inherited.

Operational notes

There are no down-migrations and no manual gate. V13 is fully superseded by V14 but remains in the path, so a fresh database inserts 411 halal spots and their cuisine rows, then deletes and re-inserts 412. A bad data migration is a restore-from-backup situation.

ddl-auto: validate makes any schema drift a boot failure, not a runtime warning. Combined with the health check, hand-editing the Supabase schema means the next deploy simply never goes live.

Do not undo V15 by disabling RLS. To read a table through PostgREST, add an explicit CREATE POLICY … FOR SELECT TO anon USING (…). Disabling RLS would re-expose the admin_users hashes.

8 · Operational gotchas

Things that will cost an afternoon if you meet them cold.

Docker Compose cannot boot the backend

Blocks local dev

The root compose file defaults SPRING_PROFILES_ACTIVE to prod but never supplies ADMIN_ALLOWED_ORIGIN, which application-prod.yml:16 requires with no default. The result is IllegalArgumentException: Could not resolve placeholder and the container dies at startup. SecurityConfig's in-code default cannot rescue it, because defaults apply when a property is absent, not when its placeholder fails to resolve.

Switching to the local profile breaks differently — it hardcodes localhost:5432, which inside the container means the container itself, not the db service. The only working path is the documented one: docker compose up -d db plus a host-side SPRING_PROFILES_ACTIVE=local mvn spring-boot:run.

The Dockerized front end talks to production

Data risk

There is no .dockerignore anywhere in the repo, so COPY . . pulls in the tracked .env.production. Vite builds in production mode, bakes in VITE_API_BASE_URL=https://suhba-backend.onrender.com, and the nginx /api/ proxy becomes dead code for public calls. Anyone running the Compose "full stack" is silently testing against live production data.

The same missing .dockerignore also lets COPY . . overwrite the freshly installed node_modules with the host's — defeating the npm ci layer cache and risking darwin/arm64 binaries inside an alpine image.

GotchaConsequence
Render free tier spins down after ~15 min idle A wake-up is a full container start — JVM boot, Spring context, Flyway check, Hibernate validate, all against a remote DB. The first visitor sees timeouts on every call, and the front end has no retry or backoff.
Cold start compounds through the proxy Cloudflare Workers cap subrequest duration, so a slow cold start can surface as an opaque 5xx from the Pages Function rather than a clean timeout.
512 MB RAM, untuned JVM No -XX:MaxRAMPercentage, so the heap defaults to roughly a quarter of the cgroup limit.
No CI anywhere Nothing runs tests before production. The backend image explicitly builds with -DskipTests. A broken build reaches Render and is caught only by the health check.
Sessions and rate limits are in-memory Every cold start logs all admins out and resets the login lockout — which, on the free tier, happens constantly.
Two abandoned host configs remain vercel.json (inert on Pages) and a Railway URL suggested in .env.example.
App data only exists for calendar year 2026 prayer_times is seeded with exactly 365 rows. A request for any 2027 date yields BLException → HTTP 400.

If you change one thing first

Add @Mapping(target = "id", ignore = true) to all three inbound mappers. It is a three-line change that closes an unauthenticated path to overwriting the entire community directory — the single highest-value edit available in this codebase.
